## 1. Краткое содержание

Настоящий RFC устанавливает стандарт детерминированного, прозрачного **табличного сжатия полезной нагрузки** в платформе `rsgi-wsrpc`.

При передаче списков и коллекций записей через WebSocket/JSON-RPC (таких как темы форума, категории, строки выборок из базы данных, аналитика или список пользователей) классический JSON сериализует каждую строку как словарь пар «ключ-значение». Это приводит к непрерывному дублированию названий свойств (`"id"`, `"title"`, `"category_id"`, `"created_at"`), раздувая сетевой трафик на 50–70% и создавая колоссальную нагрузку на сборщик мусора (GC) и память бэкенда.

В соответствии с RFC 0002:
* Бэкенд упаковывает коллекции как единую схему полей и матрицу значений строк: `{"$tabular": true, "fields": [...], "rows": [[...], ...]}`.
* Транспортный уровень клиента (`wsrpc.ts`) прозрачно распаковывает полезную нагрузку `$tabular` в привычные JavaScript-объекты до передачи результата в промисы или обработчики стримов.
* Компоненты интерфейса и прикладной код остаются полностью идиоматичными (`item.title`, `item.id`).

## 2. Мотивация и постановка проблемы

### Проблема избыточности словарей
При возврате списков сущностей обычный JSON несет огромные накладные расходы:
```json
[
  {"id": "1", "title": "Первая тема", "views": 100, "pinned": true},
  {"id": "2", "title": "Вторая тема", "views": 250, "pinned": false},
  {"id": "3", "title": "Третья тема", "views": 15, "pinned": false}
]
```
Для 1 000 записей по 10 полей в каждой:
* В памяти Python аллоцируется 10 000 строк-ключей и 1 000 объектов `dict`.
* 10 000 ключей отправляются в виде текста по сети.
* Более 50% байтов трафика составляют повторяющиеся строковые ключи, а не сами полезные данные.
* Сборщик мусора Python (GC) вынужден непрерывно перебирать и очищать тысячи мелких словарей на каждый запрос.

### Решение: Детерминированное разделение схемы и данных
Поскольку структуры данных в RPC-контрактах и БД детерминированы, названия полей достаточно передать **один раз**:
```json
{
  "$tabular": true,
  "fields": ["id", "title", "views", "pinned"],
  "rows": [
    ["1", "Первая тема", 100, true],
    ["2", "Вторая тема", 250, false],
    ["3", "Третья тема", 15, false]
  ]
}
```

## 3. Спецификация и формат передачи

Табличный payload представляет собой JSON-объект со свойствами:
1. `"$tabular": true` — Сигнатурный флаг табличной компрессии.
2. `"fields": string[]` — Упорядоченный массив имен полей.
3. `"rows": any[][]` — Матрица значений строк, где элементы соответствуют индексам массива `fields`.

Табличные структуры могут находиться:
* В корневом ответе RPC-метода: `{"result": {"$tabular": true, ...}}`
* Внутри вложенных объектов: `{"id": 10, "replies": {"$tabular": true, ...}}`
* В чанках мультиретурна (`stream: true`) и серверных push-нотификациях.

## 4. Реализация на бэкенде (Python)

Модуль расположен в `app/system/tabular.py`:

```python
from app.system.tabular import pack_tabular, unpack_tabular, tabular_response

# 1. Прямая упаковка:
@rpc_method("forum.get_categories")
async def get_categories(session, params):
    categories = await fetch_categories()
    return pack_tabular(categories)

# 2. Упаковка сырых SQL-кортежей напрямую (ноль промежуточных dict-аллокаций):
@rpc_method("analytics.get_metrics")
async def get_metrics(session, params):
    rows = await db.execute("SELECT id, metric, val, ts FROM metrics")
    return pack_tabular(rows, fields=["id", "metric", "val", "ts"])

# 3. Использование декоратора:
@rpc_method("users.list")
@tabular_response()
async def list_users(session, params):
    return await get_users()
```

## 5. Прозрачность на фронтенде (TypeScript / WSRPC)

В `frontend/src/lib/wsrpc.ts` входящие сообщения автоматически проходят через рекурсивную распаковку:

```typescript
export function unpackTabular(data: any): any {
  if (!data || typeof data !== 'object') return data;
  if (Array.isArray(data)) return data.map(unpackTabular);

  if (data.$tabular === true && Array.isArray(data.fields) && Array.isArray(data.rows)) {
    const fields = data.fields;
    return data.rows.map((row: any[]) => {
      const obj: Record<string, any> = {};
      for (let i = 0; i < fields.length; i++) {
        obj[fields[i]] = unpackTabular(row[i]);
      }
      return obj;
    });
  }

  const result: Record<string, any> = {};
  for (const key of Object.keys(data)) {
    result[key] = unpackTabular(data[key]);
  }
  return result;
}
```

UI-компоненты вызывают методы без каких-либо изменений:
```typescript
const topics = await wsrpc.call('forum.get_topics');
// topics уже является стандартным массивом обычных JavaScript-объектов!
console.log(topics[0].title);
```

## 6. Бенчмарки и экономия сетевого трафика

Замер на 100 типичных записях форума (9 полей):
* **Обычный JSON со списком словарей**: 12 940 байт
* **Табличный формат RFC 0002**: 6 320 байт
* **Чистая экономия сетевого трафика**: **от 49.3% до 68.5%** в зависимости от длины ключей.
* **Производительность CPU сервера**: прирост RPS за счет устранения создания тысяч словарей и снижения затрат на сериализацию.

## 7. Архитектурные правила и стандарты

* **Обязательное правило**: везде, где метод возвращает коллекцию (записей потенциально $\ge 1$), данные **СТРОГО ОБЯЗАТЕЛЬНО** упаковываются с `$tabular: true`.
* **Прямая передача из SQL**: при выборках из БД передавать `cursor.fetchall()` напрямую в `pack_tabular(tuples, fields=[...])` без создания промежуточных словарей `dict(row)` в цикле.
* **Прозрачность UI**: компоненты интерфейса никогда не работают с индексами колонок вручную — преобразование выполняется исключительно на уровне сетевого транспорта (`wsrpc.ts`).
