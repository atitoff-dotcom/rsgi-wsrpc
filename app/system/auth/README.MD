# Data-Driven RBAC & Row-Level Security для SQLAlchemy ORM

## Описание функционала

В системе реализован гибкий механизм контроля доступа (RBAC + Row-Level Security), встроенный на уровне SQLAlchemy событий (`do_orm_execute` и `before_flush`). Вся логика разграничения прав перенесена в базу данных (таблицы `Role` и `RolePermission`) и управляется через наследование от базовых классов безопасности.

**Основные концепции:**
- **Роли (`Role`)**: Роли хранятся в БД и содержат название и текстовое описание (например, `admin`, `Operator`, `Manager`).
- **Разрешения ролей (`RolePermission`)**: Для каждой роли настраиваются разрешения (CRUD операции) на уровне классов моделей БД.
- **Индивидуальный row-level доступ**: Флаг `row_level_only` определяет, может ли роль оперировать всеми записями модели в БД (`row_level_only = False`) или только "своими" (`row_level_only = True`), к которым относятся записи, созданные самим пользователем или членами его команд (`team_id`).

## Два типа защищенных моделей

В зависимости от бизнес-требований и структуры таблиц, защищаемые модели наследуются от одного из двух базовых классов в [core.py](file:///Users/dimat/Projects/PL3_2/app/system/auth/core.py):

### 1. Модель-ориентированная безопасность (`BasicSecureModel`)
Используется для глобальных справочников и реестров, которые не имеют владельцев (полей `creator_id` / `team_id`), но к которым необходимо разграничить доступ пользователей (например, `Bank`, `Passport`, `PassportCommission`).
- **Как это работает:** Наследуется от `BasicSecureModel`. При любых запросах к БД проверяется наличие прав `can_read` / `can_create` / `can_update` / `can_delete` на имя класса модели в разрешениях ролей пользователя. Доступ ко всем данным в таблице является глобальным (пользователь оперирует всеми строками, если право есть).
- **Схема БД:** Не требует добавления полей `creator_id` и `team_id`, что исключает конфликты первичных ключей (например, БИК для банков) и лишние столбцы в БД.

### 2. Запись-ориентированная безопасность (`RowSecureModel`)
Используется для сущностей с разделением прав на уровне записей и поддержкой командной работы (например, `Order`, `User`, `Role`, `Team`).
- **Как это работает:** Наследуется от `RowSecureModel` (которая является наследником `BasicSecureModel`). Автоматически добавляет поля `id` (PK), `creator_id`, `team_id`, `created_at` и `updated_at`.
- **Событийные фильтры:** 
  - На чтение: если у роли включен флаг `row_level_only = True`, SQLAlchemy автоматически добавляет к SQL-запросу фильтр `WHERE creator_id = :user_id OR team_id IN (:team_ids)`.
  - На запись: при сохранении новой записи поля `creator_id` и `team_id` заполняются автоматически из текущего контекста сессии.

## Архитектура проверок под капотом

1. **Контекст сессии**: При успешной аутентификации в сессию WS / HTTP прогружается контекст пользователя (`perms_dict` содержащий все разрешения, полученные путем объединения прав из всех его ролей).
2. **ContextVar**: Перед вызовом RPC-методов контекст пробрасывается в `current_user_ctx` (через ContextVar), что позволяет проверять права из любого места в рамках асинхронного таска.
3. **Обход защиты**: Системные и фоновые процессы (например, создание логов или системная инициализация) выполняют операции с БД внутри контекстного менеджера `system_bypass_ctx.set(True)`, временно отключая слушатели прав.
